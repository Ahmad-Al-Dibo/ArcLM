Developer, researcher, and contributor workflows

Application developer

Goal: ship features using ArcLM without forking it.

  1. Install the extras you need ([hf], [security], …).
  2. Prefer public packages: datasets, tokenizers, inference, agents, security.
  3. Handle OptionalDependencyError and domain errors explicitly.
  4. Use tracking for experiment metadata in your product logs.
  5. Pin the arclm version; re-run your integration tests on upgrade.

Avoid: deep imports into private helpers; relying on undocumented root aliases.

Researcher

Goal: controlled experiments, custom models/data.

  1. Start from native ArcLM + Trainer or custom nn.Module with the same trainer if compatible.
  2. Use tracking + search for sweeps.
  3. Use inspection.inspect_text to debug generation steps.
  4. Consider Blocks if you only need a subset of packages in an embedded project.
  5. Record seeds, config fingerprints, and hardware in run manifests.

Contributor

Goal: change ArcLM itself safely.

  1. Read CODEBASE_GUIDE.md (routing).
  2. Fork; install -e ".[dev,train]".
  3. Follow import boundaries (no torch in light packages).
  4. Add/adjust tests: unit + light-import + relevant suite.
  5. Update public API stubs if you change _EXPORTS.
  6. Run CI-equivalent pytest + run-verified examples.
  7. Update reference/ docs and guide if routing or API changed.

Performance / debugging

  • arclm doctor — environment and optional deps.
  • Tracking environment snapshot — torch/CUDA info per run.
  • Native model: reduce embed_dim / num_blocks first; profile with standard Python tools.
  • HF: prefer small models; check memory before raising batch size.
