Motivation and design philosophy

Why ArcLM exists

Working with language models often forces a false choice: a multi-gigabyte install before you can read one line of tokenizer code, or a pile of notebooks with no package, tests, or CLI. ArcLM was built so that data preparation, tokenization, agents, and security work on a laptop, and compute-heavy paths (native training, HF inference) are opt-in extras.

Engineering decisions (and why)

1. Light core, optional torch

pyproject.toml lists only NumPy and SentencePiece as required dependencies. The root package uses a lazy export map. Torch-backed modules call require_torch() before importing torch and raise OptionalDependencyError with an install hint. CI blocks torch at import time for light packages (tests/unit/test_light_imports.py).

Why: classrooms and app backends should not pay 500 MB for a tokenizer. Cost: more documentation and error-message care.

2. Readable packages over framework magic

Domain packages (datasets, tokenizers, training, …) are small enough to open and read. There is no single 10k-line “engine” that hides the whole pipeline. The native model is a few hundred lines of PyTorch.

Why: the primary audience includes people learning how an LLM library fits together. Cost: ArcLM is not a drop-in replacement for a large production trainer.

3. Honest limits in the product

Examples that use sshleifer/tiny-gpt2 state that output text is nonsense on purpose (fixture weights). The native model is labeled educational. Multi-GPU contracts in distributed.py are marked experimental.

4. Security fail-closed

arclm.security raises when keys or crypto libraries are missing rather than silently skipping. Agents import SecurityPolicy from arclm.security.configuration (not the package root) so the agents Block does not pull the entire crypto stack.

5. One source, many editions

distributions/ + tools/build_arclm_distributions.py generate trimmed “Blocks” (core, training, agents, security, …) from the same source using AST import analysis and hard exclude boundaries. Generated trees are rebuildable artifacts, not forks.

Extensibility model

  • Registry / factory: tokenizers via TokenizerFactory; checkpoints via SmartLoader inspectors.
  • Tools: any typed Python function becomes an agent tool via @tool.
  • Pipelines: DataPipeline chains BaseDataStep transforms.
  • Public API: extend via package __init__ + root _EXPORTS (keep __init__.pyi in sync).

Reproducibility

  • set_reproducible_seed seeds Python, NumPy (if present), and torch (if present).
  • arclm.tracking records run manifests, metrics JSONL, environment snapshots, and redacts private paths.
  • Verified examples avoid network and GPU so CI results are comparable.

Simplicity vs flexibility

High-level paths (train_model, load_dataset, CLI) trade some flexibility for fewer decisions. Lower-level paths (Trainer, native model internals, custom tools) trade convenience for control. Both live in the same package; the architecture page maps Lab / Developer / Research usage onto real modules.
