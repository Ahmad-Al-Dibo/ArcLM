The problem we kept hitting

  • Installing “just to try an API” pulls hundreds of MB
  • Docs assume GPU + multi-GB downloads on day one
  • Hard to read how data → tokens → model → eval fits together
  • Educational code and production code live in different worlds

Engineers in emerging markets & classrooms pay the highest cost for this.

What we wanted

  • Install in seconds on a laptop
  • Useful results before any training
  • Torch optional, not mandatory
  • Source small enough to study in a week
  • Same package for teaching and building apps

Who is ArcLM for?

educators & students

Classrooms with laptops, limited bandwidth, no GPU cluster.

  • Verified examples run offline on CPU
  • Lab: 32 progressive challenges
  • Native model is small enough to read

App developers

Need LLM features without owning a training stack.

  • Load HF models behind one API
  • Agents + tools without torch
  • Security helpers for logs and artifacts

Researchers / MENA teams

Embed a light toolkit; train only when the experiment needs it.

  • Blocks for trimmed installs
  • Reproducible seeds + run tracking
  • Honest limits on native models

Not trying to replace transformers as a model zoo — complements it with a readable local layer.

What ArcLM can (and cannot)

✓ Can

  • Light install (~50 MB, no torch)
  • Tokenize, validate & dedupe data
  • Load HF models & generate text
  • Train tiny native models (CPU/GPU)
  • Fine-tune with SFT / LoRA
  • Agents with typed tools
  • Encrypt, sign, redact secrets
  • Evaluate & export metrics
  • CLI + local web Studio

✗ Cannot / will not claim

  • Compete with ChatGPT / Claude
  • Native model writes useful prose
  • Every Hub model works (test per model)
  • Production multi-GPU serving
  • Replace Hugging Face as a model zoo
  • Arabic-specific LLM quality guarantees

Honesty is a feature — senior engineers trust libraries that state limits.

Core deep dive — configs, tokenizers, data

configs/

One broad Config object — plain Python, no torch.

  • Model size: embed_dim, blocks, vocab
  • Data paths, device, seed
  • create_config() with defaults
  • YAML / JSON save & load
  • No global RNG side effects (2.0 fix)

tokenizers/

Two implementations, one factory.

  • Word-level — whitespace, inspectable vocab
  • SentencePiece — BPE subwords
  • TokenizerFactory + custom registration
  • encode_text / decode
  • No auto-lowercase (explicit control)

datasets/

Records are plain dicts.

  • load_dataset — list, JSONL, CSV, TXT
  • validate_records — required fields
  • deduplicate — exact match + report
  • DataPipeline — chain cleaners
  • StreamingDataset — lazy iteration

Design rule: each package is readable in isolation. No hidden global state.

Core deep dive — agents, security, tracking

agents/

Provider-independent tool-calling runtime.

  • @tool — type hints → JSON schema
  • AgentRunner — bounded loop
  • Permissions + side-effect levels
  • Sessions, traces, approvals
  • Builtins: documents, math, safe web

security/

Fail-closed by design.

  • AEAD encrypt/decrypt + Argon2id
  • Key providers (memory, password)
  • Manifest signing + integrity
  • Path sandbox + URL checks
  • Redaction for logs/traces

tracking/ + search/

Local experiments, no cloud.

  • Run manifests + JSONL events
  • set_reproducible_seed
  • Path redaction in manifests
  • search/ = hyperparameter grid/random
  • Not semantic/IR search (name check!)

All three work without torch — useful for agent backends and data platforms.

How the core stays light — lazy loading

  • Root __init__ uses a lazy export map (~230 names)
  • import arclm does not load torch or heavy subpackages
  • First access of arclm.Trainer imports that module only
  • Heavy modules call require_torch() before import torch
  • Missing torch → clear OptionalDependencyError with install hint
# Root stays tiny
import arclm
import sys
print(arclm.get_version())
print("torch" in sys.modules)  # False

# First real use pulls one module
from arclm.tokenizers import Tokenizer
# still no torch in sys.modules

# Only training stack loads torch
from arclm.models import ArcLM  # needs [train]

This is why pip install arclm can stay ~50 MB and still expose a large API surface.

Fine-tuning path (overview)

  • SFT adapts a pretrained model to your format
  • Dataset: messages / prompt+completion / instruction
  • validate_sft_records before training
  • train_sft(..., backend="huggingface")
  • Optional LoRA via [peft] or [qlora]
from arclm.finetuning import train_sft

result = train_sft(
  model="Qwen/Qwen3-0.6B",
  dataset="sft.jsonl",
  output_dir="out/sft",
  backend="huggingface",
  use_lora=True, lora_r=8,
)

ArcLM vs common stacks (honest)

vs Hugging Face only

  • HF = model zoo + heavy deps
  • ArcLM loads HF and teaches the path
  • Complement, not replacement

vs full training frameworks

  • No distributed production stack
  • Tiny native model on purpose
  • Readable trainer, not 10k LOC

vs “notebook only”

  • Real package, CLI, tests, CI
  • Security + agents included
  • Versioned on PyPI

Choose the right tool: ArcLM for learning + light apps; HF for model access; big trainers for scale.

Training with GPU (when you have one)

Install CUDA torch first

# pick the wheel that matches your CUDA
pip install torch --index-url https://download.pytorch.org/whl/cu124
pip install "arclm[train]"

# verify ArcLM sees the GPU
arclm doctor

Doctor prints CUDA available, GPU count, name, and capability.

Use it in code / CLI

# Python
from arclm.configs import create_config
from arclm.training import train_model

config = create_config(device="cuda")  # or "auto"
train_model(..., config=config)

# CLI
arclm train --data data.txt --device cuda
  • device="auto" → CUDA if available, else CPU
  • device="cuda" → hard fail if no GPU
  • Precision: fp32 / fp16 / bf16

Multi-GPU (DDP/FSDP): experimental contracts in arclm.distributed — validate before production use. CPU remains the supported default path for teaching and CI.
